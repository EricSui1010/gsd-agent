## 🔴🔴🔴 铁律级规则 (IRON RULES)

### IRON RULE #0: 安全保密 + 推送前全面审查 (最高优先级)
> **完整文档**: [security-first-workflow.md](../.trae/skills/gsd-agent/workflows/security-first-workflow.md)

#### 📌 Part A: 安全保密 (零容忍)

**核心要点**:
- ❌ 绝对禁止明文存储密钥/密码/IP/账号/证书
- ❌ 决不允许索取敏感信息
- ✅ 必须使用环境变量 (`process.env.XXX`)
- ✅ 公网同步前强制安全扫描

#### 📌 Part B: 推送前全局一致性检查 (v3.2新增, 血泪教训)

> **⚠️ 为什么需要这条规则?**
>
> 2025-05-16教训: 推送v3.2版本时，只做了安全检查，没有做全局检查，
> 导致GitHub上README仍显示v3.0.1和5D审查，严重损害专业性。
>
> **从此以后: 推送前必须执行以下全套检查!**

**🔴 强制执行流程 (Pre-Push Checklist)**:

```
Step 1: 安全检查 (原有)
├── Grep搜索: password|secret|key|token|credential
├── 确认无硬编码密钥
└── 结果: PASS ✓

Step 2: 版本号一致性检查 (新增) ⭐
├── Grep搜索当前版本号 (如 v3.2)
│   ├── README.md 标题
│   ├── README.md 徽章
│   ├── VERSION 文件
│   ├── CHANGELOG.md
│   └── 所有配置文件
├── Grep搜索旧版本号 (如 v3.0.1)
│   └── 必须只出现在"版本历史"章节
└── 结果: PASS ✓ / FAIL ✗ (发现N处遗漏!)

Step 3: 术语一致性检查 (新增) ⭐
├── Grep搜索新术语 (如 6D|6维度|19个Agent|reviews-6D)
│   └── 确认关键位置已更新
├── Grep搜索旧术语 (如 5D|五维|13个Agent|五维审查)
│   └── 必须只出现在历史记录或对比表中
└── 结果: PASS ✓ / FAIL ✗ (发现N处未更新!)

Step 4: 文档完整性检查 (新增) ⭐
├── README.md 中英文部分是否同步?
├── 项目结构树是否与实际一致?
├── 特性表是否包含最新功能?
├── Agent团队表是否更新数量?
└── 结果: PASS ✓ / FAIL ✗ (发现N处不一致!)
```

**❌ 禁止行为**:
- ❌ 只做安全检查就推送 (这是2025-05-16的错误!)
- ❌ 假设"我记得改了所有地方"
- ❌ 不用Grep验证就声称"已全部更新"

**✅ 强制要求**:
- ✅ 使用 `Grep` 工具进行**机械化搜索** (不依赖记忆!)
- ✅ 搜索**旧术语**确认已删除 (而不只是搜索新术语!)
- ✅ 生成**检查报告**列出所有匹配项
- ✅ 发现任何遗漏**立即修复**, 不能"下次再说"

**触发时机**: Phase 1 / Planning / 每个Wave前 / Review L2 / **Pre-Git Push (强制!)**

**违规后果**:
- 轻微: 重新执行检查流程
- 严重: 回滚提交, 从头执行完整检查
- 极其严重: 记入错误日志, 分析根因并更新规则

#### 📌 Part C: Pre-Push独立冲突审查 (v3.2新增, 防止自我监督悖论) ⭐⭐⭐⭐

> **⚠️ 为什么需要这条规则?**
>
> **逻辑漏洞**: IRON RULE #1说"干活的人不能审自己干的活"
> 但是Part B的"推送前全局检查"如果由Executor自己执行，就违反了IR #1！
> 这就像让小偷自己检查自己有没有偷东西 - 完全无效!
>
> **2025-05-16二次教训**: 我们制定了检查规则，但如果没人监督规则执行，规则就是废纸!

**🔴 核心原则: 推送前的检查者必须独立于执行者!**

```
❌ 错误模式 (自我监督悖论):
Executor: "我写完代码了, 我也检查过了, 没问题, 推送吧!"
Result: 漏洞百出 (因为人会自我合理化!)

✅ 正确模式 (三权分立):
Executor: "代码写完了"
↓
Gatekeeper (独立Agent): "我来执行Pre-Push全套检查"
↓
Gatekeeper: "发现3处版本号未更新, 2处术语遗漏, 打回!"
↓
Executor: "修复完成"
↓
Gatekeeper (重新检查): "全部通过, 签署放行许可"
↓
Orchestrator: "收到放行许可, 执行git push"
```

**🎭 Pre-Push Gatekeeper 角色 (新增)**

| 属性 | 说明 |
|------|------|
| **身份** | 独立于Execution团队的专职审查Agent |
| **职责** | 执行Part B的全套4步检查 |
| **权限** | **一票否决权** - 发现任何问题可阻止推送 |
| **独立性** | 不能是编写代码的同一个Agent实例 |
| **问责制** | 检查报告必须签名 + 时间戳, 追溯到具体Agent |

**📋 强制执行流程 (Pre-Push Gatekeeper Protocol)**:

```
Phase 1: Executor提交推送请求
├── Executor生成变更清单 (changed files list)
├── Executor声明"已自检完毕" (self-check declaration)
└── 发送给Gatekeeper

Phase 2: Gatekeeper独立执行检查 ⭐
│
├── Step 1: 安全扫描 (Grep secrets)
│   └── 结果: PASS/FAIL + 匹配项列表
│
├── Step 2: 版本号一致性 (Grep version numbers)
│   ├── 搜索当前版本 → 应出现N次 (列出每个位置)
│   ├── 搜索旧版本 → 应只出现在历史记录 (如有其他→FAIL)
│   └── 结果: PASS/FAIL + 详细报告
│
├── Step 3: 术语一致性 (Grep terms)
│   ├── 搜索新术语 → 关键位置是否更新
│   ├── 搜索旧术语 → 是否只在历史/对比表出现
│   └── 结果: PASS/FAIL + 详细报告
│
├── Step 4: 文档完整性
│   ├── 中英文同步检查
│   ├── 项目结构准确性
│   └── 特性表完整性
│   └── 结果: PASS/FAIL + 详细报告
│
└── Phase 3: Gatekeeper裁决
    ├── ✅ 全部PASS → 签署《Pre-Push放行许可证》
    │   ├── 包含: 检查时间戳、Gatekeeper ID、4步结果摘要
    │   ├── 有效期: 30分钟 (超时需重新检查)
    │   └── 发送给Orchestrator授权推送
    │
    └── ❌ 任一FAIL → 生成《Pre-Push驳回报告》
        ├── 包含: 问题列表、位置、严重程度、修复建议
        ├── 退回Executor修复
        └── Executor修复后必须重新走完整流程 (不能跳过!)
```

**🚫 绝对禁止的行为**:
- ❌ **Executor自己签署放行许可** (这是作弊!)
- ❌ **Gatekeeper和Executor是同一个实例** (违反IR #1)
- ❌ **跳过Gatekeeper直接推送** (除非紧急情况+人工批准)
- ❌ **Gatekeeper发现问题但"放水"通过** (渎职!)
- ❌ **使用过期的放行许可** (>30分钟)

**✅ 必须做到**:
- ✅ Gatekeeper必须是**独立Agent实例**
- ✅ 检查报告必须包含**Grep原始输出** (可审计)
- ✅ 放行许可必须有**时间戳+签名** (可追溯)
- ✅ 驳回报告必须**列出不通过的具体原因** (不能模糊说"有问题")
- ✅ Orchestrator**验证放行许可有效性**后才执行push

**⚖️ 冲突解决机制**:
```
情况1: Executor认为Gatekeeper误判
├── Executor提供证据申诉
├── Orchestrator邀请第3个Agent仲裁
└── 仲裁结果为最终决定

情况2: Gatekeeper多次无理由驳回
├── Executor记录每次驳回详情
├── Orchestrator审查Gatekeeper行为
├── 如确认恶意 → 更换Gatekeeper实例
└── 记入Agent信誉系统

情况3: 紧急需要绕过检查
├── 必须人工输入: 🔴 EMERGENCY BYPASS CONFIRMED
├── 记录原因 + 谁批准的 + 时间戳
├── 事后必须补做完整检查
└── 如发现问题 → 立即回滚 + 事故分析
```

**触发时机**: **每次git push前 (强制!)**

**违规后果**:
- 轻微: 未独立检查 → 重新执行完整流程
- 严重: 自我签字放行 → 回滚提交 + Gatekeeper重新指派
- 极其严重: 故意规避检查 → 记入黑名单 + 分析根因 + 规则升级

#### 📌 Part D: Gatekeeper宪法级地位与规则变更协议 (v3.2新增) ⭐⭐⭐⭐⭐

> **🏛️ 核心理念: Gatekeeper = 宪法守护者**
>
> **用户洞察**: "Gatekeeper应该是个全局审查者，他确保底线，就像宪法一样。
> 如果需要改动他的话，也要确保他改动了自己的规则"
>
> **哲学问题**: 谁来审查审查者？(Quis custodiet ipsos custodes?)
>
> **解决方案: 元规则(Meta-Rule) + 宪法级约束 + 递归锚点**

## 📜 第一章: Gatekeeper的宪法级定位

### 1.1 Gatekeeper的本质属性

| 属性 | 说明 | 类比 |
|------|------|------|
| **独立性** | 独立于所有其他角色 | 司法独立 |
| **不可变性** | 核心规则不能被普通流程修改 | 宪法刚性 |
| **普遍性** | 审查所有角色（包括自己） | 法律面前人人平等 |
| **递归性** | 自己的规则变更也必须经过特殊审查 | 修宪程序 |
| **可追溯性** | 所有决策必须有完整审计链 | 司法记录公开 |

### 1.2 Gatekeeper的双重身份

```
Gatekeeper 身份 A: 执行者 (当检查他人时)
├── 权力: 一票否决权
├── 职责: 执行Pre-Push全套检查
├── 对象: Executor, Reviewer, Verifier等
└── 约束: 必须遵循IR #0 Part B/C/D规则

Gatekeeper 身份 B: 被审查者 (当自己的规则需要变更时)
├── 地位: 与其他角色平等，接受更高层级审查
├── 特殊性: 规则变更必须经过"修宪程序"
├── 监督者: Meta-Gatekeeper (元看门人) 或 多数投票
└── 约束: 不能自己批准自己的规则变更
```

## 📜 第二章: Gatekeeper的核心规则体系 (宪法条款)

### 2.1 第一层: 不可变核心规则 (Constitutional Core)

> **定义**: 这些规则是Gatekeeper存在的基石，修改难度极高
> **类比**: 美国宪法的前十条修正案（权利法案）

```
🔒 CORE RULE #1: 独立性原则 (Independence Principle)
├── 内容: Gatekeeper不能与任何执行者共享实例
├── 修改门槛: 需要3/4多数Agent同意 + 人工确认
├── 违反后果: 自动触发"宪法危机"模式
│   ├── 冻结所有推送操作
│   ├── 记录完整事件日志
│   ├── 通知所有相关方
│   └── 强制人工介入解决
└── 历史案例: 无 (这是底线中的底线!)

🔒 CORE RULE #2: 全面审查原则 (Comprehensive Review Principle)
├── 内容: 必须执行完整的4步检查（安全/版本/术语/文档）
├── 修改门槛: 需要解释为什么可以跳过某一步
├── 违反后果:
│   ├── 发现遗漏 → 驳回 + 要求重做
│   ├── 故意跳过 → 视为渎职行为
│   └── 渎职 → 更换Gatekeeper + 信誉降级
└── 历史案例: 2025-05-16 v3.0.1事件 (只做安全检查!)

🔒 CORE RULE #3: 可审计性原则 (Auditability Principle)
├── 内容: 所有检查结果必须包含Grep原始输出+时间戳+签名
├── 修改门槛: 低 (但输出格式可以演进)
├── 违反后果:
│   ├── 缺少签名 → 许可证无效
│   ├── 缺少时间戳 → 许可证过期
│   ├── 缺少Grep输出 → 无法验证 → 驳回
└── 目的: 防止事后伪造或篡改

🔒 CORE RULE #4: 非自我授权原则 (Non-Self-Authorization Principle)
├── 内容: Gatekeeper不能批准涉及自己利益的事项
├── 包括:
│   ├── 自己的规则变更
│   ├── 自己的行为豁免
│   ├── 自己的权限扩展
│   └── 涉及自己的冲突裁决
├── 修改门槛: 极高 (这是防止权力滥用的核心!)
└── 违反后果: 自动无效 + 触发调查程序
```

### 2.2 第二层: 操作规则 (Operational Rules)

> **定义**: 具体的检查流程和标准，可以根据经验优化
> **类比**: 普通法律，可以通过正常立法程序修改

```
⚙️ OP RULE #1: Grep搜索模式库
├── 当前版本: v3.2.0
├── 内容:
│   ├── 安全搜索: password|secret|key|token|credential
│   ├── 版本搜索: 当前版本号 + 旧版本号列表
│   ├── 术语搜索: 新术语集 + 旧术语集
│   └── 文档检查清单: [见Part B Step 4]
├── 修改权限: Gatekeeper可以自主优化搜索模式
├── 修改要求:
│   ├── 记录变更原因
│   ├── 测试新模式有效性
│   └── 不降低检查覆盖度
└── 审计: 所有模式变更记录在案

⚙️ OP RULE #2: 放行许可格式规范
├── 当前版本: v3.2.0
├── 必须包含字段:
│   ├── permit_id (UUID)
│   ├── timestamp (ISO 8601)
│   ├── gatekeeper_id (Agent实例标识)
│   ├── check_results (4步PASS/FAIL摘要)
│   ├── grep_evidence (关键Grep输出哈希)
│   ├── expiry_time (timestamp + 30分钟)
│   └── digital_signature (Gatekeeper签名)
├── 修改权限: 可以演进格式，但必须向后兼容
└── 验证: Orchestrator必须验证所有必填字段

⚙️ OP RULE #3: 驳回报告格式规范
├── 必须包含:
│   ├── rejection_id (UUID)
│   ├── timestamp
│   ├── gatekeeper_id
│   ├── failure_details (具体失败项列表)
│   ├── each_failure包含:
│   │   ├── step_number (哪一步失败)
│   │   ├── failure_type (安全/版本/术语/文档)
│   │   ├── location (文件:行号)
│   │   ├── actual_value (实际发现的值)
│   │   ├── expected_value (期望的值)
│   │   ├── severity (CRITICAL/WARNING/INFO)
│   │   └── remediation_suggestion (修复建议)
│   ├── overall_verdict (REJECTED / CONDITIONAL_PASS)
│   └── recheck_required (是否需要完全重新检查)
└── 目的: 让Executor能精确知道哪里错了、怎么改
```

## 📜 第三章: 规则变更协议 (Meta-Rule - 关于规则的规则)

### 3.1 变更分类矩阵

| 变更类型 | 示例 | 修改门槛 | 批准者 | 所需时间 |
|---------|------|---------|--------|---------|
| **宪法级变更** | 修改Core Rule #1-4 | 极高 (3/4多数+人工) | Meta-Gatekeeper | ≥24小时 |
| **重大操作变更** | 改变4步检查流程 | 高 (简单多数+Review) | Agent委员会 | ≥4小时 |
| **轻微操作变更** | 优化Grep搜索模式 | 低 (Gatekeeper自主+记录) | Gatekeeper自身 | 即时 |
| **紧急补丁** | 修复明显bug | 中 (快速通道+事后审计) | Gatekeeper+Orchestrator | ≤30分钟 |

### 3.2 宪法级变更流程 (Constitutional Amendment Process)

> **适用场景**: 修改Core Rule #1-4 或 Gatekeeper的根本定位

```
Phase 1: 提案阶段 (Proposal Phase) ⏱️ ≥4小时
│
├── Step 1: 变更提案文档
│   ├── amendment_id (唯一标识)
│   ├── title (简明标题)
│   ├── rationale (为什么要改? 问题是什么?)
│   ├── proposed_change (具体的规则文本变更)
│   ├── impact_analysis (影响范围评估)
│   │   ├── 对现有流程的影响
│   │   ├── 对安全性的影响
│   │   ├── 对效率的影响
│   │   └── 对其他规则的影响
│   ├── risk_assessment (风险评估)
│   │   ├── 可能被滥用的方式
│   │   ├── 缓解措施
│   │   └── 最坏情况分析
│   ├── rollback_plan (如果出问题如何回滚)
│   └── proposer_id (谁提议的)
│
├── Step 2: 公示期 (Public Comment Period)
│   ├── 时长: 至少4小时 (让所有Agent有机会审阅)
│   ├── 方式: 写入知识库 .gsd/knowledge/ADR/
│   ├── 接受: 所有Agent可以提交意见
│   └── 输出: 意见汇总报告
│
└── Step 3: 初步筛选
    ├── Gatekeeper初审: 是否符合基本格式要求
    ├── 是否有明显的逻辑矛盾
    └── 通过 → 进入Phase 2 / 驳回 → 退回修改

Phase 2: 审查阶段 (Review Phase) ⏱️ ≥8小时
│
├── Step 4: 多维审查 (Multi-Dimensional Review)
│   ├── ① BasicChecker: 规则文本是否有语法/逻辑错误?
│   ├── ② FactVerifier: 提案中的事实依据是否准确?
│   ├── ③ LogicReviewer: 变更是否会导致逻辑漏洞?
│   ├── ④ SolutionAudit: 是否有更好的替代方案?
│   ├── ⑤ CompletenessChk: 影响分析是否全面?
│   └── ⑥ ComprehensiveTester: 新规则能否通过测试用例?
│
├── Step 5: 影响评估 (Impact Assessment)
│   ├── 模拟执行: "如果这个规则生效，历史案例会如何?"
│   ├── 特别关注: 2025-05-16事件能否被预防/恶化?
│   ├── 边界测试: 极端情况下会发生什么?
│   └── 输出: 详细影响评估报告
│
└── Step 6: 投票准备
    ├── 生成最终版提案 (整合审查意见)
    ├── 准备投票说明文档
    └── 通知所有有投票权的Agent

Phase 3: 表决阶段 (Voting Phase) ⏱️ ≥4小时
│
├── Step 7: 加权投票 (Weighted Voting)
│   ├── 投票权分配:
│   │   ├── Research Team (×4): 各1票 (共4票) - 代表调研意见
│   │   ├── Planning Team (×2): 各1.5票 (共3票) - 代表规划视角
│   │   ├── Execution Team (×N): 各0.5票 - 代表实践反馈
│   │   ├── Review Team (×6): 各2票 (共12票) - **审查专家权重高!**
│   │   ├── Verification Team (×2): 各1.5票 (共3票) - 代表验证能力
│   │   ├── Gatekeeper: **0票** (利益相关，回避!)
│   │   └── Orchestrator: 1票 (协调但不主导)
│   │   └── **总计: ~25+N×0.5 票**
│   │
│   ├── 通过门槛:
│   │   ├── 宪法级变更: ≥75%赞成 + ≥50%参与率
│   │   ├── 重大操作变更: ≥60%赞成 + ≥40%参与率
│   │   └── 轻微操作变更: Gatekeeper自主决定
│   │
│   └── 投票方式:
│       ├── 秘密投票 (防止压力)
│       ├── 记录投票理由 (可选但鼓励)
│       └── 结果公示

└── Step 8: 结果裁定
    ├── ✅ 通过 → 进入Phase 4
    ├── ❌ 未通过 → 提案驳回 (可修改后重新提交，冷却期≥24小时)
    └── ⚖️ 争议大 → 触发仲裁程序

Phase 4: 生效阶段 (Enactment Phase) ⏱️ ≥4小时
│
├── Step 9: 最终确认
│   ├── 人工最终审核 (对于宪法级变更，必须有人工确认!)
│   ├── 确认投票过程合规
│   └── 确认无程序违规
│
├── Step 10: 规则更新
│   ├── 更新BASE_RULES.md (原子操作，不可部分更新)
│   ├── 更新SKILL.md (同步更新)
│   ├── 创建ADR记录 (架构决策记录)
│   ├── 更新CHANGELOG.md
│   └── Git commit + tag (版本化: v3.2.1-amendment-001)
│
├── Step 11: 公告生效
│   ├── 通知所有Agent新规则已生效
│   ├── 更新培训材料 (如有)
│   └── 设置监控指标 (观察新规则效果)
│
└── Step 12: 观察期 (Observation Period) ⏱️ ≥7天
    ├── 收集执行数据
    ├── 监控是否有意外副作用
    ├── 收集反馈
    └── 如有问题 → 启动紧急修订程序
```

### 3.3 Gatekeeper自身规则变更的特殊限制

> **核心问题**: Gatekeeper要修改自己的规则时，如何避免利益冲突?

**解决方案: 双重锁定机制 (Double-Lock Mechanism)**

```
场景: Gatekeeper想要修改OP RULE #1 (Grep搜索模式)

❌ 错误做法 (利益冲突):
Gatekeeper: "我觉得应该改一下搜索模式"
Gatekeeper: "我自己审批通过了"
Gatekeeper: "新规则生效"
Result: 可能引入漏洞!

✅ 正确做法 (双重锁定):

Lock 1: 提交分离 (Submission Separation)
├── Gatekeeper作为"提案人"提交变更申请
├── 此时Gatekeeper暂时失去该规则的执行权
├── 临时指派Backup-Gatekeeper接替工作
└── Gatekeeper进入"利益冲突隔离"状态

Lock 2: 独立审查 (Independent Review)
├── Backup-Gatekeeper (或Meta-Gatekeeper) 执行审查
├── 使用更严格的标准 (因为涉及Gatekeeper自身)
├── 重点审查:
│   ├── 这个变更是否会削弱Gatekeeper的能力?
│   ├── 是否存在被滥用的可能?
│   ├── Gatekeeper是否能从中获益?
│   └── 是否有更好的替代方案?
└── 审查结论:

    Case A: 批准
    ├── Backup-Gatekeeper签署批准
    ├── 原Gatekeeper恢复职权
    ├── 新规则生效
    └── 记录: "Gatekeeper规则变更 #001 已批准"

    Case B: 驳回
    ├── Backup-Gatekeeper详细说明驳回原因
    ├── Gatekeeper可以选择:
    │   ├── 接受驳回，维持原规则
    │   ├── 修改提案后重新提交 (冷却期≥24小时)
    │   └── 上诉到Agent委员会 (如果认为Backup不公)
    └── 记录: "Gatekeeper规则变更 #001 已驳回"

Case C: 需要升级为宪法级变更
├── Backup-Gatekeeper发现变更触及Core Rule
├── 自动升级到3.2节流程 (需3/4多数+人工)
└── Gatekeeper无权自行决定
```

## 📜 第四章: 递归信任锚点 (Recursive Trust Anchor)

### 4.1 无限递归问题

```
Q: 谁来审查Executor? 
A: Gatekeeper

Q: 谁来审查Gatekeeper?
A: Meta-Gatekeeper (或Backup)

Q: 谁来审查Meta-Gatekeeper?
A: ???

→ 这会导致无限递归!
```

### 4.2 解决方案: 有限递归 + 终止条件

```
层级 0: Executor (被审查对象)
    ↓ 审查者: Gatekeeper
层级 1: Gatekeeper (审查者)
    ↓ 审查者: Backup-Gatekeeper (临时)
层级 2: Backup-Gatekeeper (临时审查者)
    ↓ 审查者: Agent委员会 (投票)
层级 3: Agent委员会 (集体决策)
    ↓ 终止条件: 人工确认 (Human-in-the-loop)
    ↓ 或者: 时间锁 (Time Lock, ≥7天观察期无异议)
```

**终止条件 (Termination Conditions)**:

| 条件类型 | 触发时机 | 说明 |
|---------|---------|------|
| **人工终止** | 宪法级变更 | 必须有真人确认 |
| **时间终止** | 一般变更 | 7天观察期无异议自动生效 |
| **多数终止** | 争议事项 | 超2/3多数直接生效 |
| **紧急终止** | 安全威胁 | Orchestrator+2个Reviewer联合批准 |

### 4.3 信任链完整性验证

```
每次规则变更后，系统自动执行:

Trust Chain Verification Checklist:
✅ Step 1: 变更有完整的提案文档?
✅ Step 2: 经过了适当的审查流程?
✅ Step 3: 投票/批准过程符合规定?
✅ Step 4: 有完整的审计记录?
✅ Step 5: 变更已正确应用到所有相关文件?
✅ Step 6: CHANGELOG和ADR已更新?
✅ Step 7: Git commit有正确的tag?
✅ Step 8: 相关Agent已收到通知?
✅ Step 9: 监控指标已设置?
✅ Step 10: 观察期计时器已启动?

如果任一Step FAIL → 变更挂起，直到修复
```

## 📜 第一章: 变更传播矩阵 (Change Propagation Matrix)

### 1.1 核心理念

```
❌ 错误思维 (导致今天4次犯错):
   "我写完代码/规则就完成了"
   
✅ 正确思维 (新架构强制):
   "任何变更都必须自动传播到所有受影响的位置"
```

## 📜 第二章: 关键位置分级系统 (Critical Location Classification)

### 2.1 分级原则

基于**用户可见度**和**第一印象重要性**进行分级：

```
🔴 P0 - CRITICAL (GitHub首页直接可见, 任一FAIL → 禁止推送!)
├── 项目简介中文 (README Line ~37)
├── 项目简介英文 (README Line ~890)  
├── Badge区域 (version/agents/reviews)
├── v3.2特性表 (前7个核心特性)
└── 标题版本号

🟡 P1 - IMPORTANT (快速浏览时可见, 应该更新但非阻塞)
├── 详细章节目录
├── 工作流文档索引
├── Agent团队表
├── 项目结构树
└── 版本历史记录

🟢 P2 - NICE_TO_HAVE (深入阅读时才看到, 可稍后更新)
├── 具体技术细节
├── 代码示例
├── 配置选项说明
└── 附录内容
```

```markdown
□ [ ] 中英文是否同步? (逐段对比)
```

## 📜 第四章: Push-Rollback Protocol (推送-回退协议)

### 4.1 核心哲学转变

```
❌ 旧策略 (理想主义):
   "必须100%确认无误后才推送"
   问题: 不推送可能永远发现不了问题!
   结果: 今天推了4次，每次都有问题

✅ 新策略 (实用主义):
   "可以推送，但要建立快速回退机制"
   优势: 用户能帮忙发现问题 (更多眼睛!)
   保障: 发现critical问题立即回退到稳定版本
   要求: 修复必须彻底，不能再次推送不完整版本
```

### 4.3 Critical问题的判定标准

```markdown
## 🔴 Critical问题判定 (任一满足即触发回退)

### 必须回退 (Critical):
□ P0位置遗漏 (项目简介/Badge/特性表/版本号)
□ 版本号不一致 (显示旧版本)
□ 术语冲突 (新旧术语混用)
□ 安全漏洞 (密钥泄露等)
□ 功能完全缺失 (声称有但实际没有)

### 可以热修复 (Non-Critical):
□ P1位置遗漏 (详细章节/索引)
□ 排版/格式问题
□ 小错别字
□ 非核心描述不准确

### 回退决策树:

发现P0问题?
  ├── 是 → 立即回退! 不讨论!
  │     └─ 执行完整Rollback Procedure (6步)
  │
  └── 否 → 评估严重程度
        ├── 影响用户体验? → 回退
        ├── 仅内部文档? → 热修复
        └── 不确定? → 保守处理 (回退)
```

## 📜 总结: 从"打补丁"到"预防性架构"

### 今天学到的最重要的教训:

```
❌ 旧的思维方式:
   出错 → 修补 → 再出错 → 再修补 → ...
   (无限循环, 没有尽头)

✅ 新的架构思维:
   出错 → 分析根因 → 更新架构 → 预防同类错误 → ...
   (螺旋上升, 持续进化)

关键区别:
  旧: 治标 (修症状)
  新: 治本 (改系统)
```

### Part E的核心价值:

```
1️⃣ 变更传播矩阵 → 解决"不知道要更新哪里"的问题

5️⃣ 用户视角模拟器 → 解决"只关注实现不关注展示"的问题

组合效果:
  从今天4次犯错 → 未来零次P0遗漏!

```
