## 🔴🔴🔴 铁律级规则 (IRON RULES)

### IRON RULE #0: 安全保密铁律 (最高优先级)

> **优先级**: 超越所有其他规则 | **执行**: 强制 | **容忍度**: 零

#### Part A: 安全保密 (零容忍)

| 规则 | 说明 |
|------|------|
| ❌ **禁止明文存储** | 密钥/密码/IP/账号/证书 → 用 `process.env.XXX` |
| ❌ **禁止索取敏感信息** | 不要求用户填入密码/密钥 |
| ✅ **必须指导变量化** | 教用户用 `.env` / 配置文件 / 密钥管理服务 |
| ✅ **公网同步前强制审核** | GitHub推送前必须完整安全扫描 |

#### Part B: 推送前全局一致性检查 (4步全套)

> **⚠️ 血泪教训**: 只做安全检查就推送会导致版本号/术语/文档不一致！

```
Step 1: 安全检查 ✓
├── Grep: password\|secret\|key\|token\|credential
└── 确认零硬编码密钥

Step 2: 版本号一致性 ⭐
├── Grep当前版本(如v1.0): 确认所有位置已更新
├── Grep旧版本: 确认只在历史记录中出现
└── PASS / FAIL

Step 3: 术语一致性 ⭐
├── Grep新术语: 确认关键位置已更新
├── Grep旧术语: 确认只在历史/对比表出现
└── PASS / FAIL

Step 4: README完整审阅 ⭐⭐⭐ ⭐⭐⭐ (新增!)
├── ✅✅✅ 必须逐行阅读 README.md 全文!
├── [ ] 标题/Badge版本号正确?
├── [ ] 项目简介描述准确?
├── [ ] 特性表与实际功能一致?
├── [ ] 无残留旧版本引用?
└── PASS / FAIL → 发现问题立即修复!
```

**❌ 绝对禁止**:
- 只做安全检查就推送
- 不用Grep验证就声称"已全部更新"
- 未审阅README就执行git push

**✅ 必须做到**:
- 使用Grep工具进行机械化搜索
- 搜索旧术语确认已删除
- push前必须完整阅读README.md全文

#### Part C: Pre-Push Gatekeeper 独立冲突审查

**三权分立架构**:
- **Executor**: 写代码 + 自检声明
- **Gatekeeper**: 独立执行全套检查 + 一票否决权
- **Orchestrator**: 验证放行许可 + 执行 git push

**❌ 绝对禁止**:
- Executor自己签署放行许可
- 无Gatekeeper许可直接推送
- Gatekeeper"放水"通过

#### Part D: README Push前强制审阅规则 ⭐⭐⭐⭐⭐

> **新增规则 (v1.0)**: 每次git push之前，必须完整阅读README.md全文！

**触发条件**: 每次 `git push` 之前

**执行流程**:
```
1. Read工具读取 README.md 全文
2. 逐行检查:
   ├── [ ] 标题版本号正确? (应为v1.0)
   ├── [ ] Badge版本号正确?
   ├── [ ] 项目简介描述准确?
   ├── [ ] 特性表与实际功能一致?
   ├── [ ] Version History正确?(如有)
   ├── [ ] 无残留旧版本引用?
   └── [ ] 无拼写/格式错误?
3. 发现问题 → 立即修复 → 重新审阅
4. 全部通过 → 记录时间戳 → 执行push
```

**违规后果**: 
- 未审阅就push → 回退 + 记录错误案例
- 审阅不仔细导致错误 → 双倍审阅惩罚

### IRON RULE #1: 审查分离原则

**核心原则**: 干活的人不能审自己干的活（零容忍）

| 规则 | 说明 |
|------|------|
| ❌ **禁止自我审查** | Executor不能签署自己的放行许可 |
| ✅ **强制独立性** | Gatekeeper必须是独立实例 |
| ✅ **信息屏障** | 审查者不能被审查对象影响 |

### IRON RULE #2: TDD强制执行

**核心原则**: 先写测试，再写实现（不可跳过）

```
TDD循环 (强制):
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│   RED       │ → │   GREEN     │ → │   REFACTOR  │
│ 写失败测试   │    │ 最小实现     │    │ 重构优化     │
└─────────────┘    └─────────────┘    └─────────────┘
     ↑                                        │
     └────────────────────────────────────────┘
              (强制循环，不可跳过)
```

### IRON RULE #3: 质量门槛

| 指标 | 最低要求 | 目标值 |
|------|---------|--------|
| 测试覆盖率 | ≥80% | ≥90% |
| L1设计等级 | ≥B | ≥A |
| Zoom-Out分数 | ≥75 | ≥85 |
| 一致性对齐 | ≥95% | ≥98% |
| 严重问题数 | =0 | =0 |

## 🎯 工作流程规范

### Phase 1: 深度共识（唯一人工确认点）

```
Step 1: 读取项目规则 (.gsd/rules/)
Step 2: GRILL-ME 追问 (16-50个问题)
Step 3: ASSUMPTIONS MODE (生成假设+请求纠正)
Step 4: 知识库初始化 (CONTEXT.md/ADR)
         ↓
    [用户确认] ⏸
```

### Phase 2: 专业团队编排执行（全自主）

```
Research (×4并行) → Planning (×2循环) → Execution (×N+TDD) 
→ Review (6D+) → Verify (×2) → [质量门禁]
```

### Phase 3: 质量交付 & 知识进化

```
完整报告 → 知识库更新 → 规则文档更新(如有重大变化)
```

**仅在以下2种情况请求人工介入：**

| 场景 | 示例 | 处理方式 |
|------|------|---------|
